01 · Fundamentos

¿Qué es SOLID?

Cinco principios que transforman código frágil en arquitecturas robustas. Nacieron en el mundo OOP, pero hoy gobiernan cualquier paradigma serio.

📜

Origen histórico

Robert C. Martin formuló los principios a inicios de los 2000. Michael Feathers acuñó el acrónimo SOLID en 2004.

🎯

Objetivo central

Reducir acoplamiento, aumentar cohesión y permitir que el software evolucione sin desmoronarse.

🏗️

Base arquitectónica

Clean Architecture, Hexagonal, DDD, patrones GoF y prácticamente todo framework moderno dependen de SOLID.

🧠

Mentalidad correcta

No son reglas rígidas, son guías. Aplicarlas con fanatismo produce sobre-ingeniería. El equilibrio es la clave.

💡 Dato clave: SOLID no es exclusivo de la programación orientada a objetos. Sus ideas se aplican a TypeScript, Python, Go, Rust, Kotlin, Swift y prácticamente cualquier paradigma moderno.

02 · Principio S

Single Responsibility

"Una clase debe tener una sola razón para cambiar." — Robert C. Martin

S
S · R · P

Single Responsibility Principle

Principio de Responsabilidad Única
Una clase debe tener una, y solo una, razón para cambiar. Cada responsabilidad debe estar encapsulada en su propio módulo.

1 Comprensión profunda

No significa "hacer una sola cosa". Significa que todos los métodos de la clase deben pertenecer al mismo propósito funcional. Si algo cambia en el negocio, debe haber solo una razón por la que esa clase necesite modificarse.

2 Señales de violación

  • Clases con más de 300 líneas y nombres genéricos como Manager, Util, Handler
  • Mezclar lógica de negocio con persistencia, correo o presentación
  • Tests que requieren preparar 20 mocks para una sola clase
  • Un cambio en facturación rompe algo de envíos

3 Beneficios

  • Clases pequeñas, legibles, con un propósito claro
  • Menor acoplamiento, mayor cohesión
  • Tests unitarios rápidos y aislados
  • Cambios localizados sin efectos dominó

4 Ejemplo de código

❌ Violación
UsuarioService.cs 
public class UsuarioService {
  public void Guardar(Usuario u) {
    // 1. validar
    if (u.Email == null) throw ...;
    // 2. persistir
    db.Add(u); db.Save();
    // 3. email
    SendEmail(u.Email);
    // 4. log
    logger.Info("creado");
  }
}
✅ Correcto
Separado 
public class UsuarioValidator {
  public void Validar(Usuario u) {}
}
public class UsuarioRepository {
  public void Guardar(Usuario u) {}
}
public class EmailService {
  public void Enviar(string e) {}
}
public class UsuarioService {
  // solo orquesta
}
03 · Principio O

Open / Closed

"Abierto para extensión, cerrado para modificación."

O
O · C · P

Open/Closed Principle

Principio de Abierto/Cerrado
Debes poder agregar funcionalidad sin modificar código existente y probado. La abstracción es la herramienta.

1 Comprensión profunda

Cada vez que necesites una nueva funcionalidad, no deberías tocar el código ya escrito. En su lugar, extiéndelo mediante polimorfismo: interfaces, clases abstractas y patrones como Strategy o Factory.

2 Señales de violación

  • Bloques gigantes de if/else o switch discriminando tipos
  • Cada nueva variante obliga a modificar la misma clase
  • Modificar una clase rompe tests existentes que antes pasaban

3 Beneficios

  • Menor riesgo al agregar funcionalidad
  • Base de los sistemas de plugins
  • Testing más sencillo con clases aisladas

4 Ejemplo de código

❌ Violación
Descuento.cs 
public double Calc(Cliente c) {
  if (c.Tipo == "Regular")
    return c.Total * 0.05;
  else if (c.Tipo == "VIP")
    return c.Total * 0.15;
  else if (c.Tipo == "Premium")
    return c.Total * 0.25;
  // 😱 nuevo tipo → modificar aquí
}
✅ Correcto
Polimorfismo 
interface IDescuento {
  double Calcular(double t);
}
class DescuentoVIP : IDescuento {
  public double Calcular(double t)
    => t * 0.15;
}
// nuevo tipo = nueva clase,
// sin tocar nada ✨
04 · Principio L

Liskov Substitution

"Los objetos de una subclase deben poder reemplazar a los de la superclase sin romper el programa." — Barbara Liskov

L
L · S · P

Liskov Substitution Principle

Principio de Sustitución de Liskov
Las subclases deben poder usarse en lugar de la clase base sin endurecer precondiciones ni debilitar postcondiciones.

1 Comprensión profunda

Si S hereda de T, entonces donde se espere un T, debe poder usarse un S sin sorpresas. Las subclases no pueden exigir más que la base ni dar menos.

2 Señales de violación

  • Subclase lanza excepciones que la base no lanza
  • Sobrescritura con throw NotImplementedException()
  • Cliente necesita verificar el tipo real con instanceof
  • El clásico Cuadrado extends Rectángulo

3 Beneficios

  • Jerarquías de herencia coherentes
  • Polimorfismo sin condiciones ocultas
  • Código cliente más simple y robusto

4 Ejemplo clásico

❌ Violación
Cuadrado.cs 
class Rectangulo {
  virtual void SetAncho(int a) {}
  virtual void SetAlto(int h) {}
}

class Cuadrado : Rectangulo {
  override void SetAncho(int a) {
    base.SetAncho(a);
    base.SetAlto(a); // 💥
  }
}
✅ Correcto
Abstracción 
interface IFigura {
  double Area();
}

class Rectangulo : IFigura {
  public double Area()
    => Ancho * Alto;
}

class Cuadrado : IFigura {
  public double Area()
    => Lado * Lado;
}
★ 05 · Principio I — Capítulo Especial

Interface Segregation

"Los clientes no deben verse forzados a depender de interfaces que no utilizan." El principio más infravalorado y, quizá, el más transformador en la práctica diaria.

I
I · S · P

Interface Segregation Principle

Principio de Segregación de Interfaces
Es mejor tener muchas interfaces específicas que una interfaz general. Nadie debe depender de métodos que no necesita.

1 ¿Qué significa realmente?

El ISP no dice "usa interfaces pequeñas porque sí". Dice algo más profundo: una dependencia hacia una interfaz que contiene métodos que no usas es una dependencia a la que no deberías estar atado. Cada método que tu clase no necesita pero debe implementar es un punto de fragilidad futura.

Cuando alguien añade un método a esa interfaz "Dios", todas las clases que la implementan deben modificarse, incluso si nunca usarán ese método. Esa es la verdadera violación.

2 Anti-patrones que lo violan

  • Interfaz "Dios": 15 métodos que solo un subconjunto de clases usa
  • Fat Interfaces: interfaces que mezclan lectura, escritura, admin, etc.
  • Lanzar NotImplementedException: la confesión de que violaste ISP
  • Header Interfaces: interfaces creadas solo para "extraer" los métodos públicos de una clase
  • Role Interfaces mal diseñadas: agrupar métodos sin cohesión semántica

3 Beneficios medibles

  • Clases más honestas: implementan solo lo que de verdad hacen
  • Mocks de tests más simples y rápidos
  • Menor impacto al evolucionar una interfaz
  • Contratos explícitos y bien definidos por rol
  • Mejor separación de responsabilidades a nivel de tipos

4 ¿Cuándo NO aplicarlo?

Como todo en diseño, el exceso daña. No segmente interfaces por segmentar. Si dos métodos siempre se usan juntos y describen un mismo rol, mantenlos juntos. El objetivo es cohesión semántica, no fragmentación arbitraria.

💻 Ejemplo aplicado en múltiples lenguajes

ISP ejemplo en C# 
// ❌ MAL: interfaz "Dios"
public interface IMultifuncional {
  void Imprimir();
  void Escanear();
  void Faxear();
  void Fotocopiar();
}

public class ImpresoraBasica : IMultifuncional {
  public void Imprimir() { /* ok */ }
  public void Escanear()  { throw new NotImplementedException(); }
  public void Faxear()    { throw new NotImplementedException(); }
  public void Fotocopiar(){ throw new NotImplementedException(); }
}

// ✅ BIEN: interfaces segregadas por rol
public interface IImpresora  { void Imprimir(); }
public interface IEscanner   { void Escanear(); }
public interface IFax        { void Faxear(); }
public interface IFotocopiadora { void Fotocopiar(); }

public class ImpresoraBasica : IImpresora {
  public void Imprimir() { /* solo esto */ }
}

public class MultifuncionalPro :
  IImpresora, IEscanner, IFax, IFotocopiadora {
  public void Imprimir()   {}
  public void Escanear()   {}
  public void Faxear()     {}
  public void Fotocopiar() {}
}
ISP ejemplo en TypeScript 
// ✅ Interfaces segregadas por rol en TS
interface IImpresora {
  imprimir(doc: string): void;
}

interface IEscanner {
  escanear(): Documento;
}

interface IFax {
  faxear(num: string): Promise<void>;
}

class ImpresoraBasica implements IImpresora {
  imprimir(doc: string) {
    console.log(`Imprimiendo: ${doc}`);
  }
}

class Multifuncional implements IImpresora, IEscanner, IFax {
  imprimir(doc: string) {}
  escanear() { return new Documento(); }

function procesarImpresion(p: IImpresora) {
  p.imprimir("doc.pdf");
}

ISP ejemplo en Python (con ABC) 
from abc import ABC, abstractmethod

# Interfaces segregadas por rol
class Impresora(ABC):
    @abstractmethod
    def imprimir(self, doc: str) -> None: ...

class Escaner(ABC):
    @abstractmethod
    def escanear(self): ...

class ImpresoraBasica(Impresora):
    def imprimir(self, doc: str) -> None:
        print(f"Imprimiendo: {doc}")

class MultifuncionalPro(Impresora, Escaner):
    def imprimir(self, doc): ...
    def escanear(self): return "documento"
ISP ejemplo en Go (implícito) 
// Go aplica ISP de forma natural: interfaces pequeñas
type Impresora interface {
  Imprimir(doc string) error
}

type Escaner interface {
  Escanear() (string, error)
}

type Fax interface {
  EnviarFax(num string) error
}

type ImpresoraBasica struct{}

func (i ImpresoraBasica) Imprimir(doc string) error {
  fmt.Println("Imprimiendo:", doc)
  return nil
}

// Solo satisface Impresora, no las demás
// — ISP respetado sin herencia explícita
ISP ejemplo en Rust (traits) 
// Traits específicos = interfaces segregadas
trait Impresora {
  fn imprimir(&self, doc: &str);
}

trait Escaner {
  fn escanear(&self) -> String;
}

struct ImpresoraBasica;

impl Impresora for ImpresoraBasica {
  fn imprimir(&self, doc: &str) {
    println!("Imprimiendo: {}", doc);
  }
}

🔧 Refactorización paso a paso (caso real)

De un monolito de pagos a interfaces por rol

Imagina un sistema de pagos donde IPaymentGateway tiene 12 métodos. Veamos cómo aplicar ISP:

Antes — Interfaz monolítica 
public interface IPaymentGateway {
  // Cobros
  void Cobrar(Money amount);
  void Reembolsar(Refund refund);
  // Suscripciones
  void CrearSuscripcion(Plan plan);
  void CancelarSuscripcion(Id id);
  // Reportes
  Reporte GenerarReporte(Date rango);
  // Webhooks
  void RegistrarWebhook(Url url);
  // ... 6 más
}
// 😱 Cualquier gateway debe implementar TODO
↓
Después — Interfaces por rol 
public interface ICharger {
  void Cobrar(Money amount);
  void Reembolsar(Refund refund);
}

public interface ISubscriptionManager {
  void Crear(Plan plan);
  void Cancelar(Id id);
}

public interface IReporting {
  Reporte Generar(Date rango);
}

public interface IWebhookSupport {
  void Registrar(Url url);
}

// Stripe implementa todo
public class StripeGateway :
  ICharger, ISubscriptionManager,
  IReporting, IWebhookSupport { ... }

// CryptoGateway solo cobra (no tiene suscripciones)
public class CryptoGateway : ICharger { ... }

// El código cliente solo depende de lo que usa:
public class CheckoutService {
  public CheckoutService(ICharger charger) {}
}

✅ Resultado: El CheckoutService ya no depende de 12 métodos; solo de los 2 que realmente usa. Cualquier gateway que sepa cobrar puede sustituirse sin tocar nada más.

🧠 Resumen ejecutivo del ISP: Interfaces pequeñas, cohesivas y orientadas a roles. Si tu interfaz tiene métodos que nunca se llaman juntos, divídela. Si un cliente solo usa 2 de 10 métodos, tienes un problema de diseño. El ISP protege a los clientes del cambio y a los implementadores de la obligación innecesaria.

06 · Principio D

Dependency Inversion

"Depende de abstracciones, no de concreciones."

D
D · I · P

Dependency Inversion Principle

Principio de Inversión de Dependencias
Los módulos de alto nivel no deben depender de los de bajo nivel. Ambos deben depender de abstracciones.

1 Comprensión profunda

En lugar de que tu lógica de negocio dependa directamente de MySQL, MongoDB o una API externa, debe depender de una interfaz abstracta. Así puedes cambiar la implementación sin tocar el corazón de la aplicación.

2 Señales de violación

  • new ConcreteClass() dentro de clases de negocio
  • Imposible testear sin una base de datos real
  • Cambiar de framework implica reescribir la lógica

3 Beneficios

  • Inyección de dependencias natural
  • Tests unitarios con mocks triviales
  • Base de la Arquitectura Hexagonal y Clean Architecture

4 Ejemplo de código

❌ Violación
Acoplado 
public class PedidoService {
  private MySqlDb db
    = new MySqlDb();

  public void Crear(Pedido p) {
    db.Insert(p);
  }
}
✅ Correcto
Invertido 
interface IPedidoRepo {
  void Guardar(Pedido p);
}

class PedidoService {
  private readonly IPedidoRepo _r;

  public PedidoService(IPedidoRepo r) {
    _r = r;
  }

  public void Crear(Pedido p) {
    _r.Guardar(p); // abstracción
  }
}
07 · Aplicación Real

Caso Real: E-commerce

Cómo un equipo rescató un sistema monolítico con 500.000 usuarios aplicando SOLID — con énfasis en ISP.

📦 Caso de Estudio Real

De un monolito acoplado a una arquitectura mantenible

Una tienda online creció durante 4 años sin disciplina arquitectónica. Cada nueva funcionalidad tomaba semanas, los bugs se multiplicaban y los despliegues eran aterradores. Este es el plan que siguieron.

1
Diagnóstico (SRP)

Detectaron clases como OrderManager con más de 2.000 líneas: validación, cálculo, persistencia, correos y facturación todo en uno.

2
División (SRP + ISP)

Crearon OrderValidator, PriceCalculator, OrderRepository, InvoiceGenerator y EmailNotifier, cada uno con su interfaz pequeña.

3
Extensibilidad (OCP)

Reescribieron los métodos de pago con IPaymentProcessor. Agregar un nuevo método pasó de 2 semanas a 2 horas.

4
Herencia coherente (LSP)

Corrigieron jerarquías donde DigitalProduct extends PhysicalProduct rompía el cálculo de envío. Ahora ambos implementan IProduct sin herencia forzada.

5
Desacoplamiento (DIP)

Integraron inyección de dependencias. La lógica de negocio ya no sabe si persiste en PostgreSQL, MongoDB o un mock de tests.

6
Resultados medibles

Reducción del 65% en tiempo de desarrollo. Bugs en producción bajaron un 78%. Cobertura de tests pasó del 12% al 85%.

Métrica Antes Después Mejora
Tiempo de nueva feature 2-3 semanas 3-5 días ↓ 70%
Bugs por release ~45 ~8 ↓ 82%
Cobertura de tests 12% 85% ↑ 73 pts
Tiempo de onboarding 3 meses 2 semanas ↓ 85%
Excepciones NotImplemented 147 3 ↓ 98%
Métodos promedio por interfaz 12.4 2.1 ↓ 83%
08 · Por qué importa

Beneficios tangibles

SOLID no es teoría. Se traduce en métricas reales de negocio y calidad.

🧩

Mantenibilidad

Cambios localizados sin efectos dominó.

🧪

Testeabilidad

👥

Trabajo en equipo

💡

Claridad

♻️

🐛

Menos bugs

Velocidad

09 · Plan de acción

Roadmap para dominar SOLID

Una ruta progresiva desde los fundamentos hasta el nivel arquitectónico.

Fundamentos de POO

Clases, objetos, herencia, polimorfismo, encapsulamiento. Sin esta base, SOLID no se entiende.

SRP + ISP

Empieza por separar responsabilidades y crear interfaces pequeñas. Cambios de bajo riesgo, alto impacto.

OCP + DIP

Aprende abstracciones, interfaces y patrones Strategy, Factory y Dependency Injection.

LSP sutil

El más difícil de detectar. Estudia contract programming y casos clásicos como Cuadrado/Rectángulo.

Patrones GoF

SOLID es la base de Strategy, Observer, Decorator, Adapter, Factory. Estudia estos patrones.

Arquitectura limpia

Clean Architecture, Hexagonal y DDD. Aquí SOLID brilla en todo su esplendor.

Práctica real

Refactoriza legacy, contribuye a open source, escribe tests. La teoría sin práctica no se interioriza.

⚠️ Advertencia: SOLID aplicado con fanatismo produce sobre-ingeniería. No crees abstracciones antes de necesitarlas. El mejor código es el más simple que cumple el objetivo.
